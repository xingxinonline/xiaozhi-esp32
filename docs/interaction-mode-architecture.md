# 交互模式架构与方案

## 1. 文档目的

本文档用于固化智伴 AI 伴读板后续的交互模式设计。

本文档不再把 `manual` 和 `ptt` 定义为用户长期可见的主模式，而是将模式体系收口为：

1. 两种用户主模式
   - `realtime`
   - `auto`
2. 两种内部输入策略
   - `toggle/manual`
   - `ptt`

目标是在不先改服务端协议的前提下，给用户呈现更简单的模式心智，同时保留按键和语音共存所需要的内部能力。

本文档是架构与方案文档，不包含代码改动。

## 2. 背景与问题

当前项目的协议层只定义了三种监听模式：

- `auto`
- `manual`
- `realtime`

但从用户视角来看，真正需要记住的并不应该是三种协议 mode，而是“设备现在是连续对话，还是单轮对话”。

同时，设备又需要保留两类明确的按键输入语义：

1. 点击开始、再次点击结束
2. 按下开始、松开结束

如果直接把这些语义全部抬升成用户模式，就会出现几个问题：

1. 用户需要理解四个近似但不等价的模式，心智负担过高。
2. `manual` 和 `ptt` 本质上更像输入策略，而不是完整的长期工作模式。
3. `AEC`、协议 mode、按键行为会交叉耦合，后续实现容易失控。
4. 当前智伴板只有一颗主按键，更适合“少数主模式 + 多种输入策略”的方案。
5. 当前使用的是 `Custom Wake Word`，在 `Listening/Speaking` 阶段持续运行时存在明显的 CPU 和看门狗风险，因此模式设计需要优先考虑稳定性。

## 3. 设计目标

### 3.1 目标

1. 用户只需要在两种主模式中做选择。
2. 语音唤醒和按键输入可以同时存在，而不是相互替代。
3. `manual` 和 `ptt` 以内部输入策略形式保留，不要求对外暴露为长期模式。
4. 协议层继续复用现有 `auto/manual/realtime`，不要求服务端先扩协议。
5. `AEC` 从模式概念中解耦，回归为音频能力开关。
6. 方案能够适配当前 `Custom Wake Word` 的性能和稳定性约束。

### 3.2 非目标

1. 本阶段不要求服务端新增第四种 `listen.mode`。
2. 本阶段不重新设计唤醒词引擎本身。
3. 本阶段不要求所有板型统一采用相同按钮布局。

## 4. 关键定义

### 4.1 用户主模式

用户主模式是用户在设置页、MCP 工具或设备通知中真正需要理解和切换的模式，只保留两种：

1. `realtime`
   - 连续对话模式
   - 强调持续对话、较低切换成本、尽可能支持直说打断

2. `auto`
   - 单轮对话模式
   - 强调一轮一轮说话、自动收句、播报后自然结束

### 4.2 内部输入策略

内部输入策略不是用户长期保存的模式，而是设备如何解释按键动作的本地策略，共两种：

1. `toggle/manual`
   - 点击开始
   - 再次点击结束
   - 协议层使用 `manual`

2. `ptt`
   - 按下开始
   - 松开结束
   - 协议层同样使用 `manual`

### 4.3 协议层监听模式

协议层继续保持现有三种 `listen.mode`：

- `auto`
- `manual`
- `realtime`

它只负责定义一次监听会话的网络行为，不直接表达用户现在看到的产品模式。

### 4.4 打断的两种语义

后续讨论中必须明确区分：

1. 唤醒词打断
   - `Speaking` 时再次说出唤醒词，中断当前播报。

2. 直说打断
   - `Speaking` 时不说唤醒词，直接开口即可打断。

两者不能混写为“语音打断”。

## 5. 总体设计结论

### 5.1 核心结论

推荐把模式体系拆成两层：

1. 用户层只保留两种主模式：`realtime` 和 `auto`
2. 设备层保留两种输入策略：`toggle/manual` 和 `ptt`

这意味着：

1. 用户选择设备是“连续对话”还是“单轮对话”。
2. 按键系统决定本轮会话是通过点击控制，还是通过按下/松开控制。
3. `manual` 不再作为长期用户模式存在，而是作为协议层和输入策略层的内部能力。
4. `ptt` 也不再是协议扩展，而是 `manual` 的一种设备侧输入封装。

### 5.2 设计收益

1. 用户心智从四个模式收敛到两个模式。
2. 按键和语音触发可以自然共存。
3. 协议层无需先改。
4. 当前 `Custom Wake Word` 的稳定性问题可以通过“限制其持续运行范围 + 提供按钮输入策略”来规避。

## 6. 分层模型

推荐后续实现按三层组织：

### 6.1 用户主模式层

职责：

1. 决定当前长期工作模式是 `realtime` 还是 `auto`
2. 决定语音唤醒后的默认协议 mode
3. 决定播报结束后的默认状态回落策略

### 6.2 输入策略层

职责：

1. 决定按键如何发起一轮会话
2. 决定按键是否显式停止会话
3. 决定当前按钮动作是“切换式”还是“按住式”

### 6.3 协议模式层

职责：

1. 向服务端发送 `auto/manual/realtime`
2. 不表达用户的长期主模式，只表达本轮监听怎么工作

## 7. 映射关系

### 7.1 用户主模式到协议 mode

| 用户主模式 | 语音唤醒默认协议 mode | 说明         |
| ---------- | --------------------- | ------------ |
| `realtime` | `realtime`            | 连续对话优先 |
| `auto`     | `auto`                | 单轮对话优先 |

### 7.2 输入策略到协议 mode

| 输入策略        | 协议 mode | 说明                   |
| --------------- | --------- | ---------------------- |
| `toggle/manual` | `manual`  | 点击开始，再次点击结束 |
| `ptt`           | `manual`  | 按下开始，松开结束     |

### 7.3 总结

最终形成如下口径：

1. 用户层只有两种主模式。
2. 语音唤醒遵循用户主模式。
3. 按键输入可以临时走 `manual` 协议链路。
4. `ptt` 是 `manual` 的一种输入策略，而不是第四个网络模式。

## 8. 两种用户主模式定义

### 8.1 Realtime

定义：

- 设备的连续对话主模式。
- 优先使用 `realtime` 协议模式。
- 支持语音唤醒进入。
- 目标是尽可能支持唤醒词打断和直说打断。

推荐语义：

1. 唤醒词触发后进入 `Listening(realtime)`。
2. `Speaking` 结束后默认回到 `Listening(realtime)`。
3. 按键单击执行“进入或退出当前实时会话”的主动作。
4. 如需显式控制某一轮输入，按键可临时走 `manual` 或 `ptt` 策略，但不改变长期主模式。

### 8.2 Auto

定义：

- 设备的单轮对话主模式。
- 优先使用 `auto` 协议模式。
- 支持语音唤醒进入。
- 强调一轮收句、一轮回复，而不是持续开麦。

推荐语义：

1. 唤醒词触发后进入 `Listening(auto)`。
2. 当前一轮讲话结束后自动停止采集。
3. `Speaking` 结束后默认回到 `Idle`。
4. 按键可以临时走 `toggle/manual` 或 `ptt` 输入策略，增强控制感。

## 9. 两种内部输入策略定义

### 9.1 Toggle/Manual

定义：

- 用户显式开始监听。
- 用户显式结束监听。
- 设备内部通过 `StartListening()` / `StopListening()` 进入 `manual` 协议链路。

适用场景：

1. 用户希望清晰控制开始和结束。
2. 当前主模式不适合持续开麦。
3. 需要在不切换主模式的前提下，临时执行“受控输入”。

### 9.2 PTT

定义：

- 按下开始监听。
- 松开停止监听。
- 同样走 `manual` 协议链路。

适用场景：

1. 环境噪声大。
2. 当前使用 `Custom Wake Word`，希望避免持续高负载检测。
3. 儿童使用或强控制感场景。

## 10. 当前 Custom Wake Word 的约束

根据当前板上测试，`Custom Wake Word` 在 `Listening/Speaking` 阶段持续重启并参与实时检测时，会在 `audio_input` 任务中触发明显的长耗时推理，存在任务看门狗风险。

因此当前阶段的结论是：

1. `Custom Wake Word` 不宜作为 `Listening/Speaking` 阶段的通用持续检测手段。
2. `Custom Wake Word` 更适合用于 `Idle` 阶段的进入式唤醒。
3. `Speaking` 和 `Listening` 阶段的稳定控制，优先由按钮输入策略承担。
4. 对当前智伴板，`auto + ptt` 和 `realtime + toggle/manual` 的组合，比把 `manual/ptt` 暴露成长期模式更稳妥。

## 11. AEC 与模式的关系

推荐把 `AEC` 彻底定义为音频能力，而不是模式本身。

原则：

1. `AEC` 开启时，可以默认使用 `realtime`，但不代表不能切到 `auto`。
2. `AEC` 关闭时，仍然可以使用 `auto` 和按键输入策略。
3. `AEC` 状态与用户主模式应分别持久化。
4. `AEC` 状态与输入策略也应分别管理。

## 12. 智伴板推荐交互

智伴板当前只有一颗主按键，因此推荐：

### 12.1 用户层

用户只看见两个主模式：

1. 连续对话
2. 单轮对话

### 12.2 按键层

建议按键保留以下职责：

1. 单击
   - 执行当前主模式的主动作

2. 双击
   - 保留现有 `AEC` 切换

3. 三击
   - 在两种主模式之间切换：`realtime <-> auto`

4. 按下/松开
   - 用于 `ptt` 输入策略

### 12.3 推荐行为矩阵

| 当前主模式 | 语音唤醒             | 单击                           | 按下/松开          |
| ---------- | -------------------- | ------------------------------ | ------------------ |
| `realtime` | 进入 `realtime` 会话 | 进出当前会话                   | 可选地临时走 `ptt` |
| `auto`     | 进入 `auto` 会话     | 启动一轮单轮对话或停止当前一轮 | 可选地临时走 `ptt` |

结论：

1. 语音输入始终可用。
2. 按键输入始终可用。
3. 用户不需要知道 `manual`，但设备内部仍然可以使用它。

## 13. 持久化建议

### 13.1 建议存储项

建议把持久化拆成两组：

1. `chat.main_mode`
   - `0` -> `realtime`
   - `1` -> `auto`

2. `chat.button_strategy`
   - `0` -> `toggle/manual`
   - `1` -> `ptt`

`AEC` 继续独立保存，例如 `aec.mode`。

### 13.2 持久化原则

1. 默认主模式为 `realtime`。
2. 默认按钮策略可按板型决定，智伴板建议初期仍以 `toggle/manual` 为主，`ptt` 作为可选增强。
3. 模式与按钮策略分别写入 NVS。
4. 启动恢复失败时回退到 `realtime + toggle/manual`。

## 14. MCP 与远程配置建议

推荐把远程配置也收口到“主模式 + 输入策略”，而不是直接暴露协议 mode：

1. `self.audio.get_main_mode`
2. `self.audio.set_main_mode`
3. `self.audio.get_button_strategy`
4. `self.audio.set_button_strategy`
5. `self.audio.get_aec_mode`
6. `self.audio.set_aec_mode`

原则：

1. 主模式、输入策略、AEC 三者独立设置。
2. 当前有会话时，先结束当前会话再切换。
3. 切换后给出设备侧通知。

## 15. 状态机建议

### 15.1 Realtime 主模式

```text
Idle -> Listening(realtime) -> Speaking -> Listening(realtime)
```

### 15.2 Auto 主模式

```text
Idle -> Listening(auto) -> Speaking -> Idle
```

### 15.3 Toggle/Manual 输入策略

```text
Click -> Listening(manual) -> Click -> Idle -> Speaking -> Idle
```

### 15.4 PTT 输入策略

```text
PressDown -> Listening(manual) -> PressUp -> Idle -> Speaking -> Idle
```

重点是：

1. 用户主模式决定语音唤醒和默认会话流。
2. 输入策略决定按键如何临时发起一轮会话。
3. 二者是叠加关系，不是并列关系。

## 16. 分阶段落地建议

### 阶段 1：概念收口

目标：

- 用户层只保留 `realtime` 和 `auto`
- 输入层保留 `toggle/manual` 和 `ptt`

### 阶段 2：应用层抽象

目标：

- 引入主模式与按钮策略的独立抽象
- 不再把 `AEC` 当作默认模式来源

### 阶段 3：板级输入接入

目标：

- 让智伴板支持主模式切换和按钮策略切换
- 保持启动阶段的配网逻辑不受影响

### 阶段 4：MCP 与持久化

目标：

- 支持主模式、按钮策略、AEC 的查询与设置

## 17. 建议结论

推荐采用以下最终口径：

1. 用户层只暴露两种主模式：`realtime` 和 `auto`
2. 协议层继续保持 `auto/manual/realtime` 三种 `listen.mode`
3. `manual` 和 `ptt` 不再作为用户长期模式，而是设备内部输入策略
4. `ptt` 在协议上复用 `manual`
5. 语音唤醒和按键输入同时存在，不互斥
6. `AEC` 与主模式、输入策略彻底解耦
7. 对当前 `Custom Wake Word`，优先保证 `Idle` 唤醒稳定，把 `Listening/Speaking` 阶段的持续控制更多交给按钮策略

如果按这个方案推进，后续实现的复杂度会明显下降：

1. 用户心智更清晰
2. 服务端协议无需先扩展
3. 智伴板的单键交互更容易做出稳定体验
